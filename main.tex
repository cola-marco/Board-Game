\section{Game rules}
%Kalaha or Mancala?
Kalaha (also known as Mancala or Kalah) is a deterministic two-player board game consisting of two rows of six pits and two larger reservoirs called Kalahs. The objective is straightforward: to accumulate more stones in your own Kalah than your opponent. On each turn, a player selects all stones from one of their pits and redistributes them one-by-one in a counter-clockwise direction, including their own Kalah but skipping the opponent's. The game’s tactical depth arises from two key mechanics: Extra Turns, granted when the last stone lands in the player’s Kalah, and Captures, triggered when the last stone lands in an empty pit on the player’s side, allowing them to seize the stones in the opponent's opposite pit. The game concludes when one side of the board is cleared, at which point the player with the highest total count in their Kalah is declared the winner.

\section{Size space}
The state space of Kalaha, specifically the popular Kalah(6,4) variant is estimated to be between $10^{13}$ and $10^{15}$. However, when considering the game tree complexity the total number of possible move sequences the figure rises significantly, often cited between $10^{18}$ and $10^{33}$. \\
%proposed section MARCO:
\subsection*{Approximate state space estimation}
A rough upper bound for the state space of Kalaha can be obtained by observing that the game contains a fixed number of stones. In the Kalah(6,4) variant there are
\[
48 = 12 \times 4
\]
stones distributed across the board. These stones can occupy any of the 14 pits (12 regular pits and 2 stores). Ignoring game constraints, the number of ways to distribute 48 identical stones into 14 locations can be computed using the classical \textit{stars and bars} combinatorial formula:
\[
\binom{48 + 14 - 1}{14 - 1} = \binom{61}{13}
\]
which corresponds to the number of integer solutions to
\[
c_0 + c_1 + \dots + c_{13} = 48
\]
where $c_i$ represents the number of stones in pit $i$.
Evaluating this expression gives an upper bound of approximately
\[
|S| \approx 4.7 \times 10^{11}
\]
possible board configurations. \\
In practice the true state space is larger because the current player must also be considered as part of the state representation, giving approximately
\[
|S| \approx 10^{12}
\]
states. \\
This very large state space makes exhaustive search infeasible, motivating the use of depth-limited adversarial search algorithms combined with heuristic evaluation functions. \\%end
%The magnitude of this state space implies that Mancala cannot be solved by simple brute-force during real-time gameplay. This necessitates the use of heuristic search algorithms. \\
Specifically:
\begin{itemize}
    \item \textbf{Depth-Limited Search:} Algorithms like Minimax must stop at a predefined depth to remain computationally feasible, using an evaluation function to estimate the value of non-terminal states.
    \item \textbf{Efficiency:} The use of Alpha-Beta pruning is mandatory to navigate this space, as it allows the AI to ignore vast branches of the tree that are mathematically proven to be sub-optimal, focusing its resources on the most promising lines of play.
\end{itemize}
%MARCO
In a typical game state a player can choose between at most six pits, giving an approximate branching factor of $b \approx 6$. If the search depth is $d$, the theoretical complexity of Minimax search is therefore \[O(b^d)\]
which quickly becomes infeasible for large depths. For example, with $b=6$ and $d=8$, the number of explored nodes would already exceed $1.6\times10^6$. This motivates the use of Alpha-Beta pruning, which can reduce the effective branching factor and allow deeper search.


\section{Elements of the game}
%OLD: Kalaha can be formally defined as a search problem using the following components:
%MARCO:
Kalaha can be formally defined as a search problem
\[
G = (s_0, Player(s), Action(s), Result(s,a), Terminal-Test(s), Utility(s, p))
\]
where each component is defined as follows:
\begin{itemize}
    \item \textbf{Initial state $s_0$:} A board with 12 pits, each containing 4 stones, and 2 empty Kalahs.
    \item \textbf{Player(s):} Returns the player whose turn it is, the player may move multiple times if the "extra turn" rule is triggered.
    \item \textbf{Action(s):} Selecting any non-empty pit on the current player's side of the board.
    \item \textbf{Result(s,a):} The state resulting from "sowing" the stones from the chosen pit counter-clockwise, including captures and extra turn logic.
    \item \textbf{Terminal-Test(s):} True if all pits on either player's side are empty.
    \item\textbf{Utility(s,p):} Calculated at the terminal state as the difference between stones in the player's Kalah and the opponent's.
    \[
    Utility(s,p) = Store_p(s) - Store_{opp}(s)
    \]
\end{itemize}

\section{Methods \& Algorithms}
For the development of a Mancala AI, the most appropriate choice among the methods discussed in the course is the Minimax algorithm enhanced with Alpha-Beta pruning. \\
This selection is justified by the game's nature: as a deterministic, zero-sum game of perfect information, Minimax can theoretically map every possible evolution of the match to find the optimal strategy while the alpha beta pruning allow to ignore branches that are mathematically proven to be worse than previously explored options, allowing to doubles the searchable depth. \\
%MARC:
The value of a state in the \textit{Minimax} framework is defined recursively as
\[
V(s)=
\begin{cases}
Utility(s) & \text{if } Terminal-Test(s) \\
\max_{a\in Actions(s)} V(Result(s,a)) & \text{if the current player is MAX} \\
\min_{a\in Actions(s)} V(Result(s,a)) & \text{if the current player is MIN}
\end{cases}
\]
In practice the search tree must be truncated at a finite depth $d$. In that case a heuristic evaluation function $h(s)$ is used instead of the true utility value. \\
\textit{Alpha-Beta pruning} improves the efficiency of Minimax by maintaining two bounds:
\[
\alpha = \text{best value found so far for MAX}
\]
\[
\beta = \text{best value found so far for MIN}
\]
Whenever the condition
\[
\alpha \geq \beta
\]
is satisfied, the remaining branches of the search tree can be pruned because they cannot influence the final decision.


\section{Heuristics and Evaluation functions}
%MARCO:
For non-terminal states the AI player uses a heuristic evaluation function. The heuristic estimates the advantage of a player by comparing the number of stones collected in the stores:
%in the code it's used: store(player) - store(opponent)
\[
h(s,p) = Store_p(s) - Store_{opp}(s)
\]
where $Store_p(s)$ represents the number of stones in player $p$'s Kalah, while $Store_{opp}(s)$ the number of stones in the opposition player's Kalah.
This heuristic reflects the objective of the game, since the winner is determined by the number of stones in the stores. Although simple, it provides a reasonable estimate of positional advantage during search.


\section{Implemented AI's parameters}

The implemented AI player allows several parameters to be adjusted:
\begin{itemize}
\item \textbf{Search depth ($d$):} determines how many moves ahead the algorithm explores the game tree.
\item \textbf{Search algorithm:} either standard Minimax or Minimax with Alpha-Beta pruning.
\end{itemize}
In the implementation the default search depth is $d=7$. Increasing the depth generally improves playing strength but significantly increases computational cost. \\
The program also allows AI vs AI matches to benchmark different parameter settings and compare the performance of Minimax and Alpha-Beta pruning.


\section{Future work}
%MARCO:
Several improvements could further enhance the AI performance:
\begin{itemize}
\item \textbf{Improved evaluation functions:} including additional features such as the number of stones on each side of the board or potential captures.
\item \textbf{Transposition tables:} storing previously evaluated states to avoid redundant computations.
\item \textbf{Iterative deepening search:} combining depth-limited search with time constraints.
\item \textbf{Monte Carlo Tree Search:} an alternative approach often used in complex board games.
\end{itemize}
